
 ## 1. 동시다발적인 HTTP 요청과 WAS 의 멀티스레드

 클라이언트에서 WAS 로 단일 요청을 보내면 WAS 는 서블릿 컨테이너에서 해당 요청에 알맞는 서블릿을 찾아 호출한다.  
 그런데 이때, 서블릿은 구체적으로 누가 호출하는걸까?

 기본적으로 WAS 의 서블릿 호출은 스레드를 통해 실행된다.  
 즉 HTTP 요청이 오면 WAS 는 스레드를 생성하고 해당 스레드에 서블릿 호출 작업을 맡기는 것이다.

``` html
                                           Web Application Server
                                        ┌─────────────────────────────────────────────────────────────────────────┐
                                        │                                            Servlet Container            │
 ┌─────────────┐                        │ ┌─────────────┐      ┌─────────────┐      ┌────────────────────────────┐│
 │ Web browser │                        │ │             │      │ [Thread1] → │      │                            ││
 │             │  localhost:8080/hello  │ │ [request] → │ ---> │ [Thread2] → │ ---> │   run  (request, response) ││
 │             │  --------------------> │ │ [response]  │      │ [Thread3] → │      │       ↘                    ││
 │             │                        │ │             │      │             │      │         helloServlet       ││
 │             │                        │ │             │      │             │      │       ↙                    ││
 │             │   "Hello, world!"      │ │             │      │             │      │   close                    ││
 │             │  <-------------------- │ │ [response]  │ <--- │ ← [Thread4] │ <--- │  ←                         ││
 │             │                        │ │             │      │             │      │                            ││
 └─────────────┘                        │ └─────────────┘      └─────────────┘      └────────────────────────────┘│
                                        └─────────────────────────────────────────────────────────────────────────┘

```

 단일 HTTP 요청이 오면 WAS 는 스레드를 만들고 서블릿을 호출한다.  
 그런데 웹 애플리케이션은 다수의 클라이언트로부터 동시에 많은 요청을 받을 수도 있다.  
 2개 이상의 HTTP 요청이 들어온 경우에도 하나의 스레드만 사용한다면 첫 번째 요청을 처리하는 동안 스레드는 사용되고 있으므로  
 두 번째 요청은 스레드의 작업이 끝나기까지 기다려야만 한다.

 그래서 WAS 는 이런 동시다발적인 HTTP 요청에 대해 멀티 스레드 환경을 지원한다.  
 만약 다수의 클라이언트로부터 요청이 동시에 들어온다면 WAS 는 각 요청마다 스레드를 생성하고 요청을 처리한다.  
 각 요청이 하나의 스레드를 기다리지 않고 각각의 스레드를 통해 처리되기 때문에 클라이언트는 기다림 없이 자신이 보낸 요청에 대해 응답을 받는 것이다.  
 그런데 이렇게 요청이 올때마다 스레드를 생성하는 방식은 다음과 같은 몇 가지 문제가 있다.  

 ### 1) HTTP 요청마다 스레드를 계속 생성하는 경우, 발생하는 문제점.

 ☑️ 스레드의 생성 비용은 매우 비싸다.
  - HTTP 요청이 올 때마다 스레드를 생성하여 응답하게 되면 요청이 누적될수록 응답 속도가 늦어진다.

 ☑️ 스레드는 컨텍스트 스위칭 비용이 발생한다.
  - 스레드는 일반적으로 동시성으로 수행되는데, 이 과정에서 CPU 코어는 여러 개의 스레드를 번갈아가며 작업한다.
  - 이때 스레드를 바꾸는 과정에서 지속적으로 불필요한 비용이 발생한다.

 ☑️ 스레드 생성에 제한이 없다.
  - 스레드를 제한없이 계속 생성하다 보면 어느 순간 CPU 가 감당할 수 있는 한계를 넘어서고, 메모리 임계점을 넘겨 서버가 다운될 수 있다.

 때문에, 대부분의 WAS 들은 스레드풀을 사용하여 멀티 스레드를 지원한다.

 여기서 스레드풀이란, 일정 개수만큼 스레드를 생성시켜 놓고 스레드를 재활용하는 저장소를 말한다.  
 즉, WAS 는 HTTP 요청이 올때마다 제한없이 스레드를 생성하여 요청을 처리하는 것이 아니라   
 요청이 오면 스레드풀에서 대기 상태인 스레드를 호출하여 요청 처리 작업을 맡기는 것이다.   
 해당 스레드는 요청 처리를 모두 끝낸 후에 소멸되는 것이 아니라 다시 스레드풀로 돌아가 대기 상태가 되고 또 다른 요청을 위해 재사용된다.


```html 
                                           Web Application Server
                                        ┌─────────────────────────────────────────────────────────────────────────┐
                                        │                         ThreadPool         Servlet Container            │
 ┌─────────────┐                        │ ┌─────────────┐      ┌─────────────┐      ┌────────────────────────────┐│
 │ Web browser │                        │ │             │      │ [Thread1] → │      │                            ││
 │             │  localhost:8080/hello  │ │ [request] → │ ---> │ [Thread2] → │ ---> │   run  (request, response) ││
 │             │  --------------------> │ │ [response]  │      │ [Thread3] → │      │       ↘                    ││
 │             │                        │ │             │      │             │      │         helloServlet       ││
 │             │                        │ │             │      │             │      │       ↙                    ││
 │             │   "Hello, world!"      │ │             │      │             │      │   close                    ││
 │             │  <-------------------- │ │ [response]  │ <--- │ ← [Thread4] │ <--- │  ←                         ││
 │             │                        │ │             │      │             │      │                            ││
 └─────────────┘                        │ └─────────────┘      └─────────────┘      └────────────────────────────┘│
                                        └─────────────────────────────────────────────────────────────────────────┘

```

 이러한 스레드풀 방식은 다음과 같은 특징이 있다.

### 2) 스레드풀을 통한 HTTP 요청 처리의 특징

 ☑️ 최대 스레드 개수만큼 스레드를 스레드풀에 미리 생성시켜 놓고 사용한다. ( Tomcat 의 기본값 200)
  - HTTP 요청이 오면 스레드풀에서 대기 상태인 스레드를 호출하여 처리 작업을 맡긴다.
  - 작업이 다 끝나면 스레드는 소멸되는 것이 아니라 다시 스레드풀로 돌아와 대기 상태가 된다.
  - 만약 스레드풀의 모든 스레드가 사용중이라면 HTTP 요청을 거절하거나 대기하도록 할 수 있다.

 ☑️ 스레드를 미리 생성시켜 놓고 계속 재활용 하므로 스레드 생성에 대한 비용을 아낄 수 있다.  
 ☑️ 감당할 수 없을만큼 HTTP 요청이 들어오더라도, 최소한 스레드 개수만큼의 요청은 안정적으로 처리할 수 있다.

### 3) 실무에서 WAS 의 스레드풀 튜닝

 실무에서 WAS 를 튜닝해야 할 때, 가장 핵심적인 포인트는 최대 스레드 (max thread) 수이다.

 ☑️ max thread 를 너무 낮게 설정한 경우.
  - HTTP 요청이 몰렸을 때 서버 리소스는 여유롭지만(CPU 점유율 5%), 클라이언트는 금방 지연된 응답을 받게 된다.

 ☑️ max thread 를 너무 높게 설정한 경우.
  - HTTP 요청이 몰렸을 때 서버 리소스의 점유율이 급상승하고(CPU 점유율 90%), 임계점을 초과할 시 서버는 다운된다.

 ☑️ 적절한 max thread 값을 어떻게 찾을 수 있을까?
  - 애플리케이션 로직의 복잡도, CPU, 메모리 사양 등 상황마다 천차만별의 경우의 수가 존재한다.
  - 결국 성능 테스트가 중요하다.
    - 오픈하기 전, 최대한 실제 서비스와 유사하게 성능 테스트를 수행한다.
    - 성능 테스트 도구: ApacheBench, Apache JMeter, nGrinder 등

### 4) WAS 의 멀티 스레드 지원의 핵심.

 동시다발적인 HTTP 요청에 대해 WAS 는 멀티 스레드를 지원하여 처리한다.  
 다시 말해, 동시다발적인 HTTP 요청에 대한 처리 작업은 WAS 가 '대신' 맡아 처리해준다는 것이다.  
 만약 이런 WAS 의 멀티 스레드 지원이 없다면, 동시에 들어오는 HTTP 요청들에 대하여 개발자가 직접 코드를 작성하여  
 어떤 요청은 처리하고 어떤 요청은 대기시키는 등의 처리를 해야 했을 것이다.

 그러나 그럴 필요 없이 WAS 가 HTTP 요청을 맡아 처리해주므로 개발자는 멀티 스레드 관련 처리는 신경쓰지 않아도 된다.  
 마치 싱글 스레드 프로그램을 작성하듯이 비즈니스 로직에만 충실하여 소스 코드를 작성할 수 있는 것이다.  
 ❗물론 그럼에도, 개발자가 주의해야 하는 부분이 있다.  
 앞서 말했듯 서블릿은 보통 하나의 단일 인스턴스를 공유하는 방식이다. 따라서 서블릿이 가진 상태(state)에 대해 주의하며 개발해야 한다.
